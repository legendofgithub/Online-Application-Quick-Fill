## 1. 技术栈选型结论

### 1.1 结论

**选定:Electron + React + TypeScript + Vite + Electron Forge。**

| 层 | 选型 | 版本锚点 |
|---|---|---|
| 桌面容器 | Electron | ≥ 44(npm latest 实测 44.5.1,2026-10 查询 registry.npmjs.org) |
| UI 框架 | React | 19.2.x(Demo 项目 `package.json` 已锁定 `react ^19.2.8`) |
| 语言 | TypeScript | ~6.0.x(Demo 项目 `package.json` 已锁定 `typescript ~6.0.2`) |
| 构建 | Vite | ^8.3.x(Demo 项目 `package.json` 已锁定 `vite ^8.3.0`) |
| 打包分发 | Electron Forge | 8.x(npm latest 实测 @electron-forge/cli 8.0.1) |

> **对提案的一处技术修正**:输入提案写的是「内嵌 BrowserView」。`BrowserView` 自 Electron 30 起被官方废弃,后续版本已从 API 中移除,其正式替代品是 `WebContentsView`。本文统一按 **`WebContentsView`** 表述,架构意图与提案完全一致(主窗口内嵌浏览器视图加载网申页)。

**一句话理由**:用户核心诉求是「双击启动的独立工具 + 跨页面常驻的全局悬浮球 + 引导到目标页 + 自动检测 + 自动填写」五件套,四条候选路线里只有 Electron 能把这五件事在**同一个自控环境**里原生做到,且不受浏览器扩展策略、站点 CSP、脚本管理器等外部因素制约。

### 1.2 备选方案对比表

| 维度 | **Electron(选定)** | Chrome 扩展(MV3) | CDP 附加外部浏览器 | Tampermonkey 脚本 |
|---|---|---|---|---|
| ① 双击启动 | ✅ Forge 打出 Windows 安装包/便携 exe,双击即用,零前置知识 | ❌ 无独立产物:需先装 Chrome,再从商店装扩展;未上架扩展要开发者模式加载,Chrome 对旁路加载(sideload)正持续收紧,普通用户分发不可靠 | △ 工具本体可双击,但必须让 Chrome 以 `--remote-debugging-port` 启动才能附加:要么改用户日常浏览器启动参数(调试端口常开有本地安全风险),要么工具拉起独立调试实例(用户须在各招聘站重新登录) | ❌ 双重安装门槛:先装 Tampermonkey,再装脚本 |
| ② 全局悬浮球 | ✅ `frame:false + transparent + alwaysOnTop` 的 BrowserWindow,OS 级置顶,跨页面、跨应用常驻,独立于任何网页内容 | ❌ 没有真悬浮球:popup 一点到外部就关;content script 注入的浮层只活在允许注入的页面里,受页面 CSP/z-index/SPA 路由切换影响,`chrome://` 页、扩展商店、PDF 查看器等页面根本不可注入,更不能浮在其他应用之上 | ✅ 可做(独立进程 + 置顶窗) | ❌ 完全寄生于页面,无任何独立 UI |
| ③ 引导到目标页 | ✅ 悬浮球常驻引导文案;内嵌 `WebContentsView` 的导航事件(`did-navigate` 等)可主动感知"到哪了" | △ `tabs.onUpdated` + badge/pageAction 可提示,但 UI 形态弱 | ✅ `Page.frameNavigated` 可感知 | △ 仅能注入提示条到已匹配页面,做不到"未达标时主动引导" |
| ④ 自动检测 | ✅ 适配器对当前页 `executeJavaScript` 探测 DOM 特征,环境完全自控 | ✓ content script + matches 可做 | ✅ `Runtime.evaluate` 可做 | △ `@match` 注入,受站点 CSP 与脚本管理器策略影响 |
| ⑤ 自动填写稳定性 | ✅ `webContents.executeJavaScript` 从主进程注入,**不走页面 CSP 管辖**;对 React/Vue 受控组件用原生 setter + 合成事件可稳定触发 | △ 能填,但 MV3 service worker 会被浏览器休眠,长流程(逐字段 200ms 节奏)需 alarm 续命;受站点 CSP/隔离世界细节影响 | ✅ 与 Electron 能力相当 | △ 同样受站点 CSP 干扰,需依赖 GM_* API 绕行 |
| 简历本地存储 | ✅ Node 文件系统直读直写 `userData` 目录 JSON | △ `chrome.storage.local`(容量与导出迁移受限) | ✅ 自由 | △ `GM_setValue`,绑定脚本管理器 |
| 只填不提交的管控 | ✅ 填写能力收敛在主进程 `autofillService` 白名单 API,渲染层/注入脚本拿不到"提交"能力 | △ 脚本自身可不提交,但无集中管控点 | △ 同左 | △ 同左 |
| 主要代价(如实列出) | 安装包 ~100MB、内存占用偏高、需跟进 Chromium 安全更新。对低频使用的工具类产品可接受 | 依赖浏览器生态与商店政策,悬浮球诉求无解 | 本质上重复造 Electron 的事,还多出"附加浏览器失败/版本不受控/企业策略禁调试端口"风险 | 极客自用尚可,不适合作为面向普通应届生的产品形态 |
| **结论** | **选定** | 否决:诉求 ①② 无解 | 否决:体验与风险劣于 Electron | 否决:诉求 ①②③ 无解 |

### 1.3 选型理由展开(对齐五个核心诉求)

1. **双击启动**:Forge 是 Electron 官方推荐的打包链,`electron-forge package/make` 一步产出可分发的 Windows 产物;演示阶段 `vite dev` 即可跑纯前端 Demo,两阶段工具链同源(都是 Vite),无迁移成本。
2. **全局悬浮球**:这是淘汰 Chrome 扩展与 Tampermonkey 的决定性诉求。只有独立 OS 级置顶小窗口才能做到"无论用户在哪个页面、甚至别的应用里,悬浮球始终在屏幕上引导"。Electron 的 `alwaysOnTop` BrowserWindow 是四条路线中唯一原生、无 hack 的实现。
3. **引导到目标页**:悬浮球窗口 + 内嵌 `WebContentsView` 的导航事件,天然构成"引导(球上的文案/按钮)+ 判定(主进程监听 URL 变化)"闭环;不依赖用户浏览器的任何配置。
4. **自动检测**:主进程 `executeJavaScript` 探测 DOM 特征不受目标站点 CSP 限制——这是注入式填写路线里确定性最高的一种。
5. **自动填写**:与检测同一注入通道;受控组件兼容方案(原生 `value` setter + `input`/`change` 事件)在 Demo 阶段即按 MVP 口径实现(见 §4.4),Demo 验证通过的填写逻辑可直接平移。

**保留备选的定位**:Chrome 扩展路线不废弃,记入后续迭代清单,作为"已装插件用户的轻量版"补充形态;CDP 与 Tampermonkey 仅作为失败回退的技术储备,不投入开发。

### 2.2 组件职责

| 组件 | 实现 | 职责 |
|---|---|---|
| **主窗口** | `BrowserWindow`(普通带边框窗口),加载 React 简历管理页 | 简历的新建/编辑/切换"当前使用";Demo 的 `#/resume` 页直接复用为此窗口 UI |
| **悬浮球窗口** | `BrowserWindow { frame:false, transparent:true, alwaysOnTop:'screen-saver', skipTaskbar:true, resizable:false }`,加载独立的球体+面板 React 页 | 悬浮球本体(拖拽换位)、面板状态机 UI、当前简历名展示;约 64px 收起态,展开为面板 |
| **网申页视图** | `WebContentsView` 嵌入主窗口内容区(BrowserView 的现行替代 API),加载公司招聘页 | 承载真实网申页;导航事件驱动检测;`executeJavaScript` 注入探测/填写脚本 |
| **检测适配器** | 适配器模式,`SiteAdapter` 接口 + 注册表 | 逐站点适配:URL 匹配规则 → DOM 特征探测脚本 → 字段选择器映射;未知站点回落到"待机引导"态 |
| **简历数据** | 本地 JSON 文件(`app.getPath('userData')/resumes/*.json`) | 两份及以上简历,标记"当前使用";无后端、无云端,数据不出本机 |

### 2.3 SiteAdapter 接口(MVP)

```ts
interface SiteAdapter {
  id: string;                        // 如 "demo-company" | "alibaba"
  name: string;                      // 展示名,如 "演示公司" | "阿里巴巴"
  urlPattern: RegExp;                // URL 匹配,如 /campus\.example\.com\/apply/
  detectScript: string;              // 在页面上下文执行的探测脚本,返回 boolean
  // 探测脚本约定:查找表单容器特征(Demo 为 [data-campus-form],
  // 真实站点为该站的表单容器/关键输入框组合)
  fieldSelectors: FieldSelector[];   // 字段名 → 定位器 + 填写方式(text/radio/select/date/textarea)
}
```

> **本轮 Demo 不建立适配器框架**:不创建 `src/adapters/`、不实现 `SiteAdapter` 接口与注册表(那是 MVP 阶段结构,见 §4.2);Demo 的判定逻辑收敛在 `src/autofill/detector.ts`(hash===`#/apply` 且存在 `[data-campus-form]`,即 产品设计.md §4「检测逻辑(Demo 版)」),它是未来 `demo-company` 适配器 `detectScript` 逻辑的简化前身,迁移时平移进适配器即可。
>
> **urlPattern 与 Demo 检测口径的关系**:hash 属于 URL 的一部分,Demo 场景即 `urlPattern: /#\/apply$/`。urlPattern 只做**粗筛**,决定性判定一律以 `detectScript` 的 DOM 特征探测为准——与 Demo「hash + `data-campus-form`」双条件口径同构,避免仅凭 URL 误判 SPA 动态页。

### 2.5 「只填不提交」的架构落点

1. **能力收敛**:注入脚本只暴露 `detect` / `fillField` / `resetForm` 三类能力,由主进程 `autofillService` 白名单下发;preload 的 `contextBridge` 不暴露任何通用执行入口。
2. **脚本层禁令**:填写脚本模板中不存在 `submit()`、提交按钮 `click()` 等调用;表单容器的 `<form>` 不触发 `requestSubmit`/`form.dispatchEvent`。
3. **UI 层收口**:完成态文案固定为「✓ 填写完成 13/13。请人工核对后自行提交,工具不会代为提交。」,不提供任何"提交"入口。
4. **正向演示**:Demo 的 `#/apply` 设有仅供人工点击的「提交申请(演示)」按钮(§5.4),让"用户自行提交"主流程有落点;该按钮属于模拟页面元素,与铁律不冲突——工具代码永不触碰它。
5. **自测项**:走查清单含"全程无工具侧提交行为"反向专项(§7.2 第 11 条)与人工点击演示提交的正向专项(§7.2 第 19 条)。

### 2.6 IPC 安全模型

- `contextIsolation:true`、`nodeIntegration:false`(Electron 安全默认项)。
- preload 仅暴露最小 API:`getResumes()` / `setCurrentResume(id)` / `onAutofillState(cb)` / `requestStartFill()` / `requestReset()`,全部走 `ipcMain.handle` 校验后的通道。
- `WebContentsView` 不给站点任何 Node 能力;对外部站点禁用 `new-window` 自由弹窗策略在 MVP 细化。

## 5. 关键实现口径(Demo 即按 MVP 标准写)

### 5.1 受控组件填写(React/Vue 站点兼容)

```js
// filler 注入/内联执行的填写原语(Demo 与 MVP 同一口径)
const setter = Object.getOwnPropertyDescriptor(
  window.HTMLInputElement.prototype, 'value').set;
setter.call(el, value);            // 走原生 setter,绕过 React 的 value 拦截
el.dispatchEvent(new Event('input',  { bubbles: true }));
el.dispatchEvent(new Event('change', { bubbles: true }));
```

- 文本/date/textarea:`input` + `change`;单选(性别):定位对应 `radio`,`click()`;下拉(政治面貌/学历/求职意向):设 `selectedIndex` 或按 `option[value]` 选中后派发 `change`。
- 节奏:约 200ms/字段顺序填入;每填一个给该控件加短暂高亮 class(如 `.autofill-flash`,300ms 后移除)。

### 5.2 面板状态机(迁移规则)

```
      环境探测通过          点击「开始填写」         复检通过
idle ────────────▶ ready ────────────────▶ detecting ────────────▶ filling ──13/13──▶ done
 ▲ ▲                                            │                                     │
 │ │                                            │ 复检不通过(继续引导)                 │
 │ │                                            └────────────▶ idle                   │
 │ │                                              (待机·失败变体文案,见迁移表 T4 注)  │
 │ │  done ──点击「清空重填」──▶ ready(表单已清空,仍在 #/apply)                            │
 │ │                                                                                   │
 │ └──────(打断规则:离开 #/apply 或 [data-campus-form] 消失,自 ready/detecting/filling/done)│
 └─────────────────────────────────────────────────────────────────────────────────────┘
```

规范化迁移表(reducer 的唯一依据):

| # | 起点 | 事件 | 终点 | 说明 |
|---|---|---|---|---|
| T1 | idle | 环境探测通过(hash===`#/apply` 且存在 `[data-campus-form]`) | ready | 被动、持续探测,决定「开始填写」按钮是否出现 |
| T2 | ready | 点击「开始填写」 | detecting | 进入执行前复检,约 800ms |
| T3 | detecting | 复检通过 | filling | 从 1/13 逐字段填写 |
| T4 | detecting | 复检不通过 | idle | **失败分支**:回到待机引导,文案用待机态的**失败变体**(见下) |
| T5 | filling | 13/13 全部填入 | done | 完成态文案含"不代提交"声明 |
| T6 | done | 点击「清空重填」 | **ready** | 与 产品设计.md §4「状态回到『就绪』」及 §8 验收「悬浮球回到就绪态」一致 |
| T7 | ready / detecting / filling / done 任一 | 离开 `#/apply` 或 `[data-campus-form]` 从 DOM 消失 | idle | 打断规则,详见 §5.3 |

各态文案/按钮按 产品设计.md §4 状态机表逐字实现(如完成态:「✓ 填写完成 13/13。请人工核对后自行提交,工具不会代为提交。」)。

**两次检测的职责区分**(对齐产品诉求③④「点击开始填写后自动检测,不符合则继续引导」):

1. **环境探测(被动)**:悬浮球持续监听 hashchange 与 DOM,判定面板处于待机还是就绪——它只决定「开始填写」按钮是否出现,对应诉求②③的引导阶段;
2. **执行前复检(主动)**:用户点击「开始填写」后,约 800ms 的检测中状态结束时**必须重新执行一次检测逻辑**(严禁无条件放行),通过→填写中(T3),不通过→待机(T4)。待机态文案有**默认/失败两种**(与 产品设计.md §4 表格及其补充规则「双阶段检测」对齐):默认文案「悬浮球已就绪,请进入校招网申页面」用于路由不在 `#/apply` 等常规待机场景;**T4 失败变体文案逐字为「✗ 未检测到网申表单,请进入校招网申页面后再试」**(产品设计.md §8 验收逐字钉死),按钮均为「进入演示网申页」,即诉求④的「不符合则继续引导」。

**T4 失败分支在 Demo 中的可达路径**:就绪后点击「开始填写」,在 spinner 的约 800ms 内点击浏览器返回、手改 hash 离开 `#/apply`,或经 DevTools 移除 `[data-campus-form]` 容器(两种触发方式均见 产品设计.md §8)→ 复检时 hash/DOM 条件不再成立 → T4 触发。若无此分支,MVP 阶段真实站点上点击后检测失败将无状态可去。

### 5.3 路由与打断策略

| 规则 | 定义 |
|---|---|
| 默认路由 | 无 hash(空、`#/`、`#`)或未知 hash(如 `#/foo`)→ 一律 `location.replace('#/resume')` 重定向到简历管理页(用 `replace` 不污染历史栈);仅识别 `#/resume`、`#/apply` 两个路由 |
| 路由切换中的悬浮球 | 悬浮球为 App 根级组件,挂载于路由容器之外,两个页面及 hash 切换过程中**始终存在、不卸载**(对齐 产品设计.md §5.3) |
| 检测中被打断(T7) | 复检自然不通过,走 T4 同路径回待机 |
| 填写中被打断(T7) | 立即停止后续字段填写;**已填字段保留在表单中,不回滚、不继续**;用户回到 `#/apply` 后环境探测重新通过→就绪,可再次「开始填写」(填写为幂等覆盖写入,从第 1 个字段重新填入,已填值被同值覆盖,无副作用) |
| 完成态被打断(T7) | 回待机;表单内容保留;回到页面后重新探测→就绪。就绪态面板仅提供「开始填写」,再次填写从第 1 字段全量覆盖(「清空重填」按钮仅存在于完成态,见 产品设计.md §4 表格) |

> 注(打断覆盖面):产品设计.md §4 打断规则仅列「检测中/填写中」两种情形;T7 将覆盖面扩至 ready/done——就绪态或完成态下离开 `#/apply` 同样必须回待机,否则悬浮球会在非网申页继续显示「开始填写」/「清空重填」等不合时宜的操作。此为本方案对产品文档的技术性补全(必要超集),建议产品文档后续同步。

### 5.4 演示提交按钮(铁律的正向演示落点)

- `#/apply` 底部渲染一个「**提交申请(演示)**」按钮(普通 `button`,`type="button"`,不承载 `<form>` 提交语义)——按钮名与提示文案逐字对齐 产品设计.md §5.2/§8 验收;
- 人工点击行为:仅在页面内弹出「**演示提交成功:未发送任何数据**」类提示,无任何网络请求与业务动作——这让主流程第⑦步「用户自行核对并点击提交」(产品设计.md §3)在 Demo 中有落点,铁律可正向演示而非仅反向验证;
- 工具侧约束:悬浮球面板、`filler.ts`、检测逻辑中**不存在对该按钮的任何定位与触发**(§2.5 第 2 条);走查含人工点击的正向验证(§7.2 第 19 条)。
